# SmartCard 2.0

**"Instagram, but everyone in it is someone you've actually met in person."**

A private social app where every connection is created through verified physical, in-person contact — an NFC tap or a GPS-verified QR scan — and never any other way. No stranger search, no follow/following, no global directory. This is a from-scratch rebuild; nothing here shares code with the legacy SmartCard app.

Web (Next.js), iOS/Android (React Native + Expo), and a shared TypeScript core in one monorepo.

---

## Documentation standards (non-negotiable)

This project is built and maintained by AI coding agents on behalf of a non-specialist owner. That makes documentation quality a correctness requirement, not a nicety. Every contributor — human or agent — follows these rules with no exceptions:

- **Write for a senior engineer who wasn't in the room.** Every module, migration, RLS policy, and security-critical function needs documentation that explains the *why*, not a restatement of the code. If a reader would ask "why did they do it this way?", answer it in a comment or the adjoining doc — don't make them reverse-engineer intent.
- **Security and data-access decisions are documented in plain language**, not just in code. Anyone reading the repo should be able to understand *why* a check exists — what it defends against — without first understanding the implementation.
- **No decision silently diverges from the signed-off architecture.** The architecture proposal (see `docs/architecture/`) is the source of truth. If implementation reveals a reason to deviate, the deviation and its reasoning are written down where the original decision lived, not left implicit in a diff.
- **Commit messages explain why, not just what.** "Fix bug" or "update schema" are not acceptable; state the problem being solved.
- **Comments are precise and minimal, not decorative.** Don't narrate obvious code. Do capture non-obvious constraints, invariants, and the reasoning behind anything that would otherwise look arbitrary (a magic number, a specific ordering, a check that looks redundant but isn't).
- **Every database migration includes a comment block** stating what it changes, why, and — for RLS policies — exactly what access it grants or forbids and to whom.
- **README and phase docs are updated as part of the change that makes them stale**, not as cleanup work later.

Treat this as the standard a professional architect would hold a team to on a codebase that handles real people's location data and identity. Sloppy or absent documentation on this project is a defect, on par with a bug.

**Connect Flow landed 2026-08-13** (architecture §4 — the most security-critical part of the product; each subsection of §4 now carries a "built" amendment recording what was decided along the way). Four new migrations, the QR+GPS and NFC verification paths, four API routes, and the first real contents of `packages/core`. Five things a reader should know:

- **There is now a test runner, and the threat model is a test suite.** Vitest at the root, wired into `turbo.json`, so `pnpm turbo test` runs everything — 193 tests, 176 of them in `packages/core`. They are adversarial rather than happy-path: an old token, a consumed session, a scan from another continent with a perfectly valid current code, two junk failures trying to buy a wider radius, a revoked card, injection-shaped input. **The suite was verified capable of failing** by temporarily breaking the distance comparison (11 tests went red, including all three video-relay tests) and then restoring it. A test that cannot fail proves nothing.
- **Only one thing can write the social graph, and it is enforced twice.** In the database, by there being no INSERT policy and no INSERT grant on `connections`/`meetings`/`meeting_participants`/`meeting_locations` for any client role — re-verified against the live database as a simulated authenticated user, where every direct insert is refused with `42501`. And in TypeScript, by a branded type only the verifiers can produce, so writing `createVerifiedConnection(store, { ok: true, … })` in an API route is a compile error rather than a code-review catch.
- **The multi-table write is one Postgres transaction, not six HTTP calls.** `supabase-js` has no client-side transaction, and the partial states six calls can leave are security-relevant — the worst leaves the meeting written and the session still live, which is the screenshot-and-forward attack reopened by a dropped connection. It is a `security definer`-adjacent choice deliberately made the *other* way: `security invoker`, so a mistaken grant hits the absent INSERT policies instead of bypassing them.
- **Rejections tell the user nothing.** Never the distance, the radius, or anything about the other party — a rejection that returned the computed distance would let anyone holding a valid token stand in three places and trilaterate the presenter's position. A blocked caller gets the same words as an ordinary failure; all three card refusals are identical so the endpoint is not a card-code oracle. This is tested as a rule (no digits, no threshold vocabulary), not reviewed as copy.
- **The card-tap notification mechanism is real, and there are currently zero registered tokens for anybody.** That is expected — mobile auth and token registration need the EAS dev build. It sends through Expo, marks dead tokens disabled, and never blocks or reverses a connection on failure; it logs loudly instead, because the failure mode to avoid is a notification pipeline that has been dead for a week. The *in-app* half of that detection control is a real remaining gap, tracked as Q28.

**Auth bridge landed 2026-08-13** (architecture §5, Q7 resolved — see the §5.4 amendment for the evidence and the reasoning). Until this existed, `auth.uid()` returned nothing and every RLS policy denied every row for every client: the schema failing closed exactly as designed, but also the reason the migration checklist's most important line — "spot-check RLS as a real migrated user" (§6.6) — could not be run, because it could not tell "RLS is correctly protecting this user's data" from "everything is denied because auth is not wired up". **That check has now been run against a real migrated user and passes**: their own row, social links and cards are visible; every other user's row, links and cards return zero; no session at all still returns nothing. Three things a reader should know:

- **Supabase cannot be pointed at Kinde directly, and this was checked rather than assumed.** Third-Party Auth still supports only a named list (Clerk, Firebase, Auth0, Cognito, WorkOS). More decisively, `auth.uid()` casts the token's `sub` to a uuid and every Kinde id is `kp_<32 hex>` — a raw Kinde token makes policies *error*, not deny. So our API verifies the Kinde token against Kinde's JWKS, resolves it to a `users` row, and mints a 5-minute Supabase token whose `sub` is that row's id.
- **New accounts are created server-side, never by the client.** A client able to insert its own `users` row is a client able to choose its own `kinde_user_id` — which is choosing which account it is. That one function is the only thing in the app that uses the service-role key; everything else queries through RLS.
- **Two secrets are still needed** before the flow can be exercised over real HTTP: `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET`, both from the Supabase dashboard. `.env.local` says exactly where.

**Auth signing key migrated 2026-08-13** (architecture §5.4's second amendment, Q27; `apps/web/src/server/auth/supabase-token.ts`). The bridge was signing its per-request Supabase tokens with the project's *previous* JWT key — a shared secret Supabase keeps alive only until outstanding tokens expire and can revoke without warning, which would fail every request for every user at once. It now signs **ES256** with a P-256 key this app owns. Three things a reader should know:

- **The question this turned on had a two-sided answer, and both sides mattered.** Supabase holds the private half of the project's current key and will not export it ("extracting of the private key or shared secret from Supabase is not possible"), so signing with *that* key is impossible for us — but importing a key *we* generate is the documented, first-class mechanism for an app that mints its own tokens. Supabase's Custom Access Token hook, which looks like the modern answer, is a dead end here and was checked rather than assumed: it decorates a token Supabase Auth is already issuing, and `auth.users` holds **0 rows** against `public.users`' 337, because Kinde is the sole identity provider.
- **Only the signature changed.** Five-minute lifetime, `sub` = `public.users.id`, `role: authenticated`, minted per request, never stored, server-side only — all preserved, and now asserted by tests instead of by reading the code, including a field-by-field comparison of old- and new-signed tokens. A real token was minted with the real key and verified against the live database as a real migrated user: `auth.uid()` resolves, own row/links/cards visible, every other user's denied — the same numbers as the original bridge check.
- **It is not finished until somebody clicks two buttons.** Importing and rotating a signing key is a dashboard step no tooling here can perform (the same wall as the two secrets above). The keypair is generated and waiting in `.env.local` with the JSON to paste and the exact order; until then the app still signs with the legacy secret and says so loudly in the log at every start. Related trap, written down before anyone hits it: **do not revoke the legacy JWT secret** — `SUPABASE_SERVICE_ROLE_KEY` is itself a legacy JWT signed with it (tracked as Q31).

**Mutual connections + meeting record landed 2026-08-13** (README build order item 3; `apps/web/src/app/connections/`, `apps/web/src/server/connections/connections-service.ts`). A connections list and a per-connection meeting-record view, consuming the schema and the RLS policies in `20260809211200_rls_policies_graph_and_meetings.sql` exactly as they already stood — no migration, no policy, and no line of `packages/core/src/connect/` or the Connect Flow API routes changed. Three things a reader should know:

- **Every mutation this feature offers maps to exactly one existing column-level UPDATE grant, checked against the migration before writing any code, not assumed from the architecture doc's prose.** "Share with mutual connections" writes `meetings.location_visibility` only (the grant also covers `is_private`, which this pass deliberately exposes no control for — see the next point); each participant's "agree to share" and "mark this meeting private" write their own `meeting_participants.location_share_consent` / `marked_private` row only; removing a connection writes `connections.status: active -> removed`, the one transition the policy allows a client to make at all. **Meeting feed landed 2026-08-13** (README build order item 4 — the last of the core Phase 1 pilot features; architecture §2.9; `apps/web/src/app/feed/`, `apps/web/src/server/feed/feed-service.ts`). A single `/feed` page listing every meeting the signed-in user is entitled to see, consuming `private.can_see_meeting()` and the `meetings`/`meeting_participants`/`meeting_locations`/`connections`/`users` policies in `20260809211200_rls_policies_graph_and_meetings.sql` and `20260809211100_rls_policies_identity_and_cards.sql` exactly as they already stood — no migration, no policy, and no line of `packages/core/src/connect/`, the Connect Flow API routes, or `apps/web/src/app/connections/**` changed, beyond the one new link a participant feed item makes into `/connections/[connectionId]`. Per §2.9, there is still no feed table: both post types are computed on every read from the same three tables the schema always had. Four things a reader should know:

- **The security boundary is one unfiltered `SELECT` on `meetings`, and every other query in the service layer just formats what RLS already decided.** `listFeedItems` (`feed-service.ts`) runs `select * from meetings order by occurred_at desc limit 50` through the caller's own RLS-bound client with no `.eq(...)`, no participant filter, and no mutual-of-both check written in TypeScript anywhere — `private.can_see_meeting()` is the only thing deciding which rows come back. This was verified by reading that function and the policy migration directly (not assumed from the architecture doc's prose) before any code was written, including confirming the `users` select policy's `are_connected` branch already permits reading *both* participants' profiles for a triadic post, since the viewer is by definition connected to both.
- **"You met X" vs "[A] met B" is a five-line pure function with its own adversarial test file** (`apps/web/src/app/feed/classify.ts` / `.test.ts`), following the same pattern as the connections feature's `location-sharing.ts`: given a meeting's participant ids and the viewer's id, it returns `"participant"` if the viewer is one of the two, `"mutual"` if not, and `null` — fail closed, skip the row — if the meeting isn't a well-formed two-participant row. It does not re-derive graph membership; that would duplicate the RLS check rather than trust it.
- **Location follows the same "never approximate" rule as everything else here.** `meeting_locations` is queried plainly, through the same RLS-bound client, for every meeting in view. For a participant's own meetings that's usually a row; for triadic posts it is almost always nothing, because sharing needs unanimous consent from participants who don't know this particular viewer exists at consent time — expected and correct, not a gap to work around.
- **Judgment call — a sane cap, not pagination.** The task's own sizing note (and §2.9's ~337-user scale) says pilot users have a single-digit number of meetings on day one; the feed is a plain reverse-chronological list capped at 50 rows, with no cursor, no infinite scroll, and no machinery aimed at a scale this product doesn't have yet. Worth revisiting — with real pagination, not a bigger number — once a pilot user's meeting count approaches the cap.

**Deployed to Vercel 2026-08-13** — the web app is live at `https://smart-card-2-0-web-smart-card1.vercel.app`, verified by fetching `/` and `/profile` directly rather than trusting a green build: `/profile` correctly renders the signed-out gate with a real `/api/auth/login` link, confirming the Kinde env vars resolve at request time in production, not just during the build's static analysis. Two things a reader should know:

- **Turborepo silently strips server-only env vars from a task unless `turbo.json` declares them, independent of whether Vercel has them set.** The build failed twice with `KINDE_ISSUER_URL is required` even after every variable was confirmed present on the Vercel project — the build log's own warning named the cause. - **A pasted `SUPABASE_SERVICE_ROLE_KEY` came out of the browser corrupted, and it took a live production error to catch.** Every request past a successful Kinde login failed with `Cannot convert argument to a ByteString because the character at index 8 has a value of 8226` — a literal bullet character (`•`) sitting inside the key, most likely a Chrome password-manager overlay interfering with a bulk multi-line paste into Vercel's env var form. The build had nothing to say about it (a malformed secret is still a valid string at build time); it only surfaced once `ensureUser()` tried to use it as a real Supabase `Authorization` header at request time, verified by reading the actual runtime error via `get_runtime_errors` rather than guessing from the symptom. **QR presenter froze on "Setting up your code…" in production, found by a real user testing the nav shell.** `presenter-flow.tsx`'s requesting-location effect dispatches `starting` partway through its own async body, before `createQrSession` resolves. Its dependency array is `[state.phase]`, so that self-dispatched phase change tore the effect's own instance down mid-flight, running the cleanup that set the `cancelled` flag the rest of that same instance was still checking — the session was created successfully (confirmed 201s in the runtime logs) and the `session-started` dispatch that renders the QR was silently dropped. The `failed` dispatch in the catch branch had the identical race, never reported because nobody had hit it yet. Per CLAUDE.md's model guidance for connection-security code, diagnosed here but fixed with Opus at high effort: replaced the cleanup-driven flag with a ref-based attempt id that only increments on a genuine new attempt (initial mount or `restart`), not on every phase change the effect causes on its own way to finishing. `scanner-flow.tsx` was checked for the same pattern and doesn't have it — its effects only ever dispatch as the last step of their sequence.

**Events landed 2026-08-14** (README build order item 5 — the last of the Phase 1 pilot features; architecture §2.6, and its new "Completed (2026-08-14)" subsection; `supabase/migrations/20260814051000`–`20260814051400`, `packages/core/src/events/`, `apps/web/src/server/events/`, `apps/web/src/app/(app)/events/actions.ts`). Cities, capacity, host approval, a waitlist, event cover images, and the two-count "who's going" hook. **Backend only — there are no screens**, by design: the project owner is building the UI separately, so this pass ships the schema, the policies, the RPCs, the service layer and the Server Actions those screens will call. Two long-open questions closed with it: **Q5** (anyone signed in may create an event) and **Q14** (no recurrence concept — one row per occurrence). Five things a reader should know:

- **Nobody can write an RSVP status any more, and that is the point of the whole pass.** The original policy let a client insert and update `event_rsvps.status` directly, which was fine when the four statuses were things you could truthfully say about yourself. Adding capacity and host approval changed what `going` *means*: a client that can write `going` can approve itself past the host's gate and take a seat at a sold-out event. Worse, `going` is one of the three branches deciding who may read whose profile (`shares_event_with`, §3.4) — so a writable `going` is a writable profile-visibility grant. All three write grants and all three write policies are now gone, and every transition goes through one of three `security definer` functions that compute the real status themselves while holding a lock on the event. This is the same shape `connections` and `meetings` have always had, for the same reason. Verified against the live database as a real authenticated user: direct `INSERT`, `UPDATE` and `DELETE` on `event_rsvps` are all refused with `42501`.
- **A "going" RSVP to an event that already ended is now refused, and that is a security fix rather than tidying.** Two people who both RSVP `going` to the same event can read each other's profiles. Without this check, every public event in the archive was a permanent standing invitation: pick a person, find an event they attended last month, tap "going", read their profile — no attendance, no contact, nothing they could notice or refuse. Now it takes a live, upcoming event both people are choosing to be at, which is the situation that rule was actually designed for.
- **The host's approval queue shows names, and that disclosure is contained in one function on purpose.** A host cannot approve a request from a name they can't see, so the queue has to reveal profile fields for people the host may not otherwise be able to read. The obvious way to do that — add a branch to the `users` read policy — was considered and **rejected**: that policy is what structurally forbids global search, and a branch there would apply to every query against `users` anywhere in the app, forever. Instead it is one `security definer` function that answers one question, for one role, about one event, and can't be composed into anything else. It deliberately excludes people who only tapped "interested", people who said no, and people already denied.
- **Waitlist promotion happens inside the transaction that frees the seat, never on a timer.** A seat filled "shortly after" is a seat that briefly belongs to nobody, and a queue where the next person can't take their own seat but anyone refreshing can is a race, not a queue. Withdrawing, changing your answer, or a host raising the capacity all promote from the front of the line (oldest first, tie-broken deterministically) in the same commit. Raising capacity from 1 to 3 with two people waiting promotes both, verified live; lowering it again demotes nobody, because an admission already given is not withdrawn by editing a number.
- **The city list is a placeholder and is meant to be edited.** Ten US metros are seeded so the feature works end to end; that is not a decision about where SmartCard operates. Cities are a curated table rather than free text (four spellings of "New York" within a week would break the only query browse needs) and rather than geocoded (that buys a vendor and an unresolved terms-of-service question — Q25 — to solve a problem the pilot doesn't have). Clients get SELECT and nothing else; editing the list is a service-role job. Deactivating a city hides it from browse without touching the history of what happened there — deleting one that has events is refused outright.

**Reverse geocoding landed 2026-08-14, closing Q25** (architecture §2.4 amendment, §9; `apps/web/src/server/connect/geocode.ts`). `meeting_locations.place_label` had been null for every QR/GPS meeting since the Connect Flow pass, because the job that fills it needed a provider decision this pass makes. Five things a reader should know:

- **This deliberately reverses a property the product used to have, and should be read as such.** `/card/<code>` previously rendered a static prompt and touched the database *zero* times, so a real code and a garbage code returned byte-identical pages. - **Rate limiting had to be invented, because §4.6's controls do not reach an anonymous caller.** Every limit that resists brute-forcing a card code is keyed to a user — `nfc-verifier.ts` says so in as many words — and there is no account to charge here. They are deliberately tighter than the connect limits, which inverts §4.6's sizing call on purpose: a connect limit that bites breaks the product in front of pilot users, whereas a preview limit that bites shows a stranger a courtesy page and is fixed by one `UPDATE`.

**The card preview was widened to the whole profile, later on 2026-08-15** (`20260809211100`'s new amendment, architecture §2.8 and §4.7 threat 1's second amendment, `DESIGN.md` §6's "Profile as a visitor sees it" note; `apps/web/src/server/cards/card-preview-service.ts`, `apps/web/src/server/cards/vcard.ts`, `apps/web/src/components/`). Four things a reader should know:

- **This reverses a rule that was written down, and the reversal is recorded where the rule lives.** `20260809211100` said exposing `social_links` outside the profile's own gate "would be a searchable directory of people's off-platform handles bolted onto a product whose premise is that strangers cannot find you." The owner decided otherwise, and the argument for why it is still permitted is that the objection is to **discovery**, which this path has none of: the only inputs are still a card code or a signed QR token, and there is no query anywhere that takes a handle or a name and returns a person. That is now enforced rather than asserted — the §4.7 threat 4 source scan that has guarded `users` since the Connect Flow runs against `social_links` too, so a `.or()` or `.ilike()` added to that table anywhere in the repo fails the build. - **The ring counts are service-role aggregates, and they are counts in the strict sense.** Neither number is readable through RLS by anyone but the subject (`connections` returns only your own edges; other people's RSVPs are not visible), so there was no policy to write. They are computed with PostgREST's `head: true`, which answers with a count header and an **empty body** — no row, no name, no id of anybody counted ever crosses the wire, which is the property that makes running them without a policy behind them defensible. Counting distinct labels and calling them "cities" would be a number the app cannot stand behind, so the band is omitted rather than approximated. The same reasoning retired the prototype's "Happening near you" heading on Home: there is no user location anywhere in the schema, so the section is "Coming up" and lists the viewer's own answered events.
- **Feed builds one of the spec's two card shapes on purpose.** The other is "photo posts, full-bleed" — and a meeting carries no photo in this schema, with an open photo feed on CLAUDE.md's out-of-scope list. The prototype fills that half with a striped placeholder block, which is exactly the "forced placeholder" §6 rules out. The pass did add one thing of substance: `listFeedItems` has been returning the event a meeting was tagged to since 2026-08-14 and nothing rendered it. It is on the card now.
- **Editing a profile moved to `/profile/edit`.** `/profile` used to *be* three stacked forms with no view of the profile they were editing; §6 specifies a viewing screen with a floating Edit pill, which only means something if the pill has somewhere to go. The forms moved unchanged — same components, same Server Actions, same validation, same RLS. The one behavioural change is revalidation: the actions now refresh both paths, since a save made on the edit screen has to land on the view the person returns to as well as on the form they are looking at.
- **Two prototype details were changed to clear the accessibility floor.** §8 sets a 44px touch target, and the prototype's feed row puts its only link behind a 32px circular arrow button — so the whole card is the link and the arrow is decoration. And Profile's email-preference toggle is a *reading* of stored state on a viewing screen, so it carries an explicit "On"/"Off" word rather than leaning on the accent colour alone.

**Three backend gaps behind finished-looking screens were closed 2026-08-15** (`apps/web/src/server/events/attendance-count.ts`, `apps/web/src/server/events/cover-upload.ts`, `apps/web/src/app/(app)/profile/email-opt-in-toggle.tsx`, plus amendments in `docs/design/DESIGN.md` §6 where each departure was originally recorded). Each was a control or a number that looked right and was not backed, and in all three cases the *reason* it had been left was a real constraint written down at the time rather than an oversight — so each fix removes the constraint rather than working around it. **No migration, no new RLS policy, no new grant, and no new service-role caller.** Three things a reader should know:

- **The email toggle was a picture, and making it a control needed a narrower write than the one that existed.** `email_opt_in` rendered on Profile as a word and a painted pill because the only action writing that column, `updateProfileAction`, submits the whole profile form — a lone toggle posting to it would have carried seven absent fields and blanked somebody's name, bio and phone number in order to turn off a mailing preference. `updateEmailOptInAction` writes that one column, through the same `updateOwnProfile` service function and the same column-level UPDATE grant from `20260809211100` that already permitted it (`userProfileUpdateSchema` is `.partial()`, so a single-key update was always valid). The switch renders stored state only — no optimistic flip — because a switch that moves on a failed write tells somebody they have opted out when they have not, and §8's "colour is never the only signal" survives intact: "On"/"Off" is the switch's own visible label, with `role="switch"` and `aria-checked` saying the same thing to assistive tech.
- **Event covers upload after the event exists, because the object key *is* the access control.** `uploadEventCover` had existed since 2026-08-14 with no caller, so every event rendered the striped placeholder. The key is `{event_id}/cover.{ext}` and the Storage policies parse the event id back out of it to ask `private.is_event_host` — checked against the live database rather than read off the migration: `storage.objects` carries exactly four `event-covers` policies, all `to authenticated`, with INSERT/UPDATE/DELETE each requiring the caller to be the host, SELECT gated by `can_see_event`, and `anon` named by none of them; the bucket is private, 5 MiB, JPEG/PNG/WEBP. So a cover cannot exist before its event: there is no id to key it under and no host for a policy to check. Staging the bytes under a temporary prefix was rejected (it needs a policy for a path with no event behind it, which gives away the "malformed key denies" property the bucket rests on), as was uploading inside the create action (a two-step publish that can half-fail after the form has navigated away). The control lives on the dark host panel of `/events/[eventId]`, which already means "only you can do this", and the create form lands there on success. The extension is derived from the media type out of a fixed map, never from the filename, so this app can only ever ask for keys the policies accept.
- **Profile's "events attended" undercounted past 50, and the fix is one function rather than a second correct one.** Profile derived the number in TypeScript from `listAttendingEvents`, which caps at the 50 most recent RSVPs — right for a browse list, wrong as the input to a count — so a person with 51 qualifying RSVPs saw 50 on their own profile while `/card/<code>`, counting in SQL, showed strangers the true figure. Both surfaces now call `countEventsAttended`, which counts with `count: "exact", head: true` (a count header and an empty body: no row, no id, no name crosses the wire, which is the property that makes it safe on the card preview's service-role client where no policy stands behind it). A failed count now omits the ring band instead of taking the page down or drawing a zero, since "0 events attended" is a claim and not an absence. The regression test is the case the old code got wrong: with 63 qualifying RSVPs the counter answers 63 while the old list-derived route answers 50, asserted side by side against the same fake, and **verified capable of failing** by two mutations — dropping the `going` filter (1 red) and rebuilding the count on a capped row list (4 red, including "expected 50 to be 63") — each restored.

**Onboarding and self-serve account deletion landed 2026-08-15** (architecture §2.1's "Resolved 2026-08-15" amendment, §2.6's and §3.4's new amendments, and three of them on `20260809211100`; `supabase/migrations/2026081513*`, `apps/web/src/app/onboarding/`, `apps/web/src/server/onboarding/`, `apps/web/src/server/account/`, `apps/web/src/app/(app)/settings/`). Two features that were each blocked by the same thing: a column with no writer, and a `status` value with no implementation. **The four migrations in this pass are written but NOT applied** — they are files for review, unlike every other migration referenced above. Five things a reader should know:

- **`has_completed_signup` finally has a writer, and it is deliberately not one a client can reach.** The column has existed since the first schema migration and had never been written by anything, so it read false on every account and could only ever read false — which is why the three designed onboarding screens were never built. The fix is a service-role UPDATE in one module, plus a backfill (`20260815130000`) marking **every row that existed** as complete, so onboarding only ever happens to accounts created after that point and nobody mid-pilot is ambushed by a setup wizard for an account they already have. The `security definer` RPC pattern the RSVP write path uses was weighed and rejected here: those RPCs are safe to grant because the client's request is an *input to a computation*, and a `complete_signup()` that takes no evidence and writes `true` would just be the client claiming completion, spelled differently. `no-second-write-path.test.ts` now fails if any file besides the service and the row's Zod schema names the column in code.
- **The escape hatch is a correctness requirement, not a courtesy.** The gate in `(app)/layout.tsx` is unconditional and every field the flow collects is optional, so a path to the end of onboarding that did not write the flag would return the person to setup forever with nothing they could type to escape. Both exits write it, and a test asserts the skip path does. `/onboarding` lives outside the `(app)` route group so the gate needs no "except this page" branch — a layout is never told the pathname, which is the same limitation the sign-in screen records.
- **Deleting an account is one transaction, and the reason is the card.** `public.soft_delete_own_account()` marks the account deleted, **revokes every card the person owns**, cancels the events they host and burns any live QR session — together or not at all. The partial state that motivates this is specific: "account deleted, cards not revoked" leaves a permanent URL printed on a physical object still answering `/card/<code>` with a phone number and an email address. Four sequential PostgREST calls would produce it on any dropped connection. The function takes **no arguments** — the subject is read from the JWT — so "deleted the wrong person" is not a bug this code can have.
- **It is a soft delete, and the copy is held to that.** An administrator can restore the account and the events this cancelled (`public.restore_deleted_user`, service-role only), so the confirmation must not say "permanent" or "cannot be undone" — §7's rule against inventing a capability applies equally to inventing a limitation, and a person who believed it was irreversible would never ask for the reversal that exists. The old test banning the phrase "delete your account" from the codebase is replaced by one asserting the opposite failure. The one thing the restore will not do is re-arm the cards: `cards.status` records no reason, so the database cannot tell a card this revoked from one the owner revoked after losing it, and the copy says so.
- **Two visibility rules changed, both narrowing, both recorded where the original decision lives.** A `deleted` user's row is no longer readable through the connection or co-attendee branches of the `users` policy — until now account status affected authentication only, so a deleted member would have stayed in everyone's lists indefinitely. And a cancelled event leaves the "any authenticated user may see a public event" branch of `can_see_event` while staying visible to its host, its invitees and everyone who already answered, which is the whole point: attendees are owed the news rather than a disappearance. Connections, meetings and RSVP rows are deliberately untouched — flipping `connections` to `removed` is one-way, and doing it here would make the soft delete irreversible in the dimension that matters most. 40 new tests (333 in `apps/web`, 289 in `packages/core`), verified capable of failing by three mutations: removing the card revocation from the delete transaction (2 red), adding the completion flag to the client-writable profile schema (1 red), and writing the flag through the RLS-bound client (1 red), each restored.

See the architecture proposal for the full stack, schema, RLS strategy, and connection-verification design; §3.6 records the judgment calls made while implementing the schema, and the 2026-08-13 amendments record theirs the same way. Build order for the first pilot:

1. Profile
2. Connect flow — NFC + QR/GPS (highest security priority)
3. Mutual connections + meeting record
4. Meeting feed, including the triadic "A met B" post
5. Events — RSVP + "who's going"

Messaging is deferred past the first pilot. So is the **pending-connection** half of the non-user flow (architecture §2.8) — capturing a *non-user's* details so a member gets something out of meeting them. The **preview** half — showing a *cardholder's* details to a non-user who tapped their card — was built 2026-08-15; the two point in opposite directions and are complements rather than stages, which §2.8's amendment sets out in a table.

## Getting started

**Prerequisites:** Node 22+, and [Corepack](https://nodejs.org/api/corepack.html) enabled (`corepack enable && corepack prepare pnpm@latest --activate`) — this repo uses pnpm workspaces + Turborepo, pinned via `packageManager` in `package.json`, so plain `npm`/`yarn` won't work correctly here.

```sh
pnpm install
```

**Web (Next.js):**

```sh
pnpm --filter web dev
```

**Mobile (Expo):**

```sh
pnpm --filter mobile start
```

NFC work later in the build order needs an EAS development build, not Expo Go — see `docs/architecture/` §7.2.

**Environment variables** come from a single `.env.local` at the repo root (gitignored — never committed). Both apps' dev scripts load it directly rather than keeping a per-app copy. If it's missing, ask the project owner for values.
