# SmartCard 2.0

**"Instagram, but everyone in it is someone you've actually met in person."**

A private social app where every connection is created through verified physical, in-person contact — an NFC tap or a GPS-verified QR scan — and never any other way. No stranger search, no follow/following, no global directory. This is a from-scratch rebuild; nothing here shares code with the legacy SmartCard app.

Web (Next.js), iOS/Android (React Native + Expo), and a shared TypeScript core in one monorepo.

---

## Documentation standards (non-negotiable)

This project is built and maintained by AI coding agents on behalf of a non-specialist owner. That makes documentation quality a correctness requirement, not a nicety. Every contributor — human or agent — follows these rules with no exceptions:

- **Write for a senior engineer who wasn't in the room.** Every module, migration, RLS policy, and security-critical function needs documentation that explains the *why*, not a restatement of the code. If a reader would ask "why did they do it this way?", answer it in a comment or the adjoining doc — don't make them reverse-engineer intent.
- **Security and data-access decisions are documented in plain language**, not just in code. Anyone reading the repo should be able to understand *why* a check exists — what it defends against — without first understanding the implementation.
- **No decision silently diverges from the signed-off architecture.** The architecture proposal (see `docs/architecture/`) is the source of truth. If implementation reveals a reason to deviate, the deviation and its reasoning are written down where the original decision lived, not left implicit in a diff.
- **Commit messages explain why, not just what.** "Fix bug" or "update schema" are not acceptable; state the problem being solved.
- **Comments are precise and minimal, not decorative.** Don't narrate obvious code. Do capture non-obvious constraints, invariants, and the reasoning behind anything that would otherwise look arbitrary (a magic number, a specific ordering, a check that looks redundant but isn't).
- **Every database migration includes a comment block** stating what it changes, why, and — for RLS policies — exactly what access it grants or forbids and to whom.
- **README and phase docs are updated as part of the change that makes them stale**, not as cleanup work later.

Treat this as the standard a professional architect would hold a team to on a codebase that handles real people's location data and identity. Sloppy or absent documentation on this project is a defect, on par with a bug.

**Connect Flow landed 2026-08-13** (architecture §4 — the most security-critical part of the product; each subsection of §4 now carries a "built" amendment recording what was decided along the way). Four new migrations, the QR+GPS and NFC verification paths, four API routes, and the first real contents of `packages/core`. Five things a reader should know:

- **There is now a test runner, and the threat model is a test suite.** Vitest at the root, wired into `turbo.json`, so `pnpm turbo test` runs everything — 193 tests, 176 of them in `packages/core`. They are adversarial rather than happy-path: an old token, a consumed session, a scan from another continent with a perfectly valid current code, two junk failures trying to buy a wider radius, a revoked card, injection-shaped input. **The suite was verified capable of failing** by temporarily breaking the distance comparison (11 tests went red, including all three video-relay tests) and then restoring it. A test that cannot fail proves nothing.
- **Only one thing can write the social graph, and it is enforced twice.** In the database, by there being no INSERT policy and no INSERT grant on `connections`/`meetings`/`meeting_participants`/`meeting_locations` for any client role — re-verified against the live database as a simulated authenticated user, where every direct insert is refused with `42501`. And in TypeScript, by a branded type only the verifiers can produce, so writing `createVerifiedConnection(store, { ok: true, … })` in an API route is a compile error rather than a code-review catch.
- **The multi-table write is one Postgres transaction, not six HTTP calls.** `supabase-js` has no client-side transaction, and the partial states six calls can leave are security-relevant — the worst leaves the meeting written and the session still live, which is the screenshot-and-forward attack reopened by a dropped connection. It is a `security definer`-adjacent choice deliberately made the *other* way: `security invoker`, so a mistaken grant hits the absent INSERT policies instead of bypassing them.
- **Rejections tell the user nothing.** Never the distance, the radius, or anything about the other party — a rejection that returned the computed distance would let anyone holding a valid token stand in three places and trilaterate the presenter's position. A blocked caller gets the same words as an ordinary failure; all three card refusals are identical so the endpoint is not a card-code oracle. This is tested as a rule (no digits, no threshold vocabulary), not reviewed as copy.
- **The card-tap notification mechanism is real, and there are currently zero registered tokens for anybody.** That is expected — mobile auth and token registration need the EAS dev build. It sends through Expo, marks dead tokens disabled, and never blocks or reverses a connection on failure; it logs loudly instead, because the failure mode to avoid is a notification pipeline that has been dead for a week. The *in-app* half of that detection control is a real remaining gap, tracked as Q28.

**Auth bridge landed 2026-08-13** (architecture §5, Q7 resolved — see the §5.4 amendment for the evidence and the reasoning). Until this existed, `auth.uid()` returned nothing and every RLS policy denied every row for every client: the schema failing closed exactly as designed, but also the reason the migration checklist's most important line — "spot-check RLS as a real migrated user" (§6.6) — could not be run, because it could not tell "RLS is correctly protecting this user's data" from "everything is denied because auth is not wired up". **That check has now been run against a real migrated user and passes**: their own row, social links and cards are visible; every other user's row, links and cards return zero; no session at all still returns nothing. Three things a reader should know:

- **Supabase cannot be pointed at Kinde directly, and this was checked rather than assumed.** Third-Party Auth still supports only a named list (Clerk, Firebase, Auth0, Cognito, WorkOS). More decisively, `auth.uid()` casts the token's `sub` to a uuid and every Kinde id is `kp_<32 hex>` — a raw Kinde token makes policies *error*, not deny. So our API verifies the Kinde token against Kinde's JWKS, resolves it to a `users` row, and mints a 5-minute Supabase token whose `sub` is that row's id.
- **New accounts are created server-side, never by the client.** A client able to insert its own `users` row is a client able to choose its own `kinde_user_id` — which is choosing which account it is. That one function is the only thing in the app that uses the service-role key; everything else queries through RLS.
- **Two secrets are still needed** before the flow can be exercised over real HTTP: `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET`, both from the Supabase dashboard. `.env.local` says exactly where.

**Auth signing key migrated 2026-08-13** (architecture §5.4's second amendment, Q27; `apps/web/src/server/auth/supabase-token.ts`). The bridge was signing its per-request Supabase tokens with the project's *previous* JWT key — a shared secret Supabase keeps alive only until outstanding tokens expire and can revoke without warning, which would fail every request for every user at once. It now signs **ES256** with a P-256 key this app owns. Three things a reader should know:

- **The question this turned on had a two-sided answer, and both sides mattered.** Supabase holds the private half of the project's current key and will not export it ("extracting of the private key or shared secret from Supabase is not possible"), so signing with *that* key is impossible for us — but importing a key *we* generate is the documented, first-class mechanism for an app that mints its own tokens. Supabase's Custom Access Token hook, which looks like the modern answer, is a dead end here and was checked rather than assumed: it decorates a token Supabase Auth is already issuing, and `auth.users` holds **0 rows** against `public.users`' 337, because Kinde is the sole identity provider.
- **Only the signature changed.** Five-minute lifetime, `sub` = `public.users.id`, `role: authenticated`, minted per request, never stored, server-side only — all preserved, and now asserted by tests instead of by reading the code, including a field-by-field comparison of old- and new-signed tokens. A real token was minted with the real key and verified against the live database as a real migrated user: `auth.uid()` resolves, own row/links/cards visible, every other user's denied — the same numbers as the original bridge check.
- **It is not finished until somebody clicks two buttons.** Importing and rotating a signing key is a dashboard step no tooling here can perform (the same wall as the two secrets above). The keypair is generated and waiting in `.env.local` with the JSON to paste and the exact order; until then the app still signs with the legacy secret and says so loudly in the log at every start. Related trap, written down before anyone hits it: **do not revoke the legacy JWT secret** — `SUPABASE_SERVICE_ROLE_KEY` is itself a legacy JWT signed with it (tracked as Q31).

**Mutual connections + meeting record landed 2026-08-13** (README build order item 3; `apps/web/src/app/connections/`, `apps/web/src/server/connections/connections-service.ts`). A connections list and a per-connection meeting-record view, consuming the schema and the RLS policies in `20260809211200_rls_policies_graph_and_meetings.sql` exactly as they already stood — no migration, no policy, and no line of `packages/core/src/connect/` or the Connect Flow API routes changed. Three things a reader should know:

- **Every mutation this feature offers maps to exactly one existing column-level UPDATE grant, checked against the migration before writing any code, not assumed from the architecture doc's prose.** "Share with mutual connections" writes `meetings.location_visibility` only (the grant also covers `is_private`, which this pass deliberately exposes no control for — see the next point); each participant's "agree to share" and "mark this meeting private" write their own `meeting_participants.location_share_consent` / `marked_private` row only; removing a connection writes `connections.status: active -> removed`, the one transition the policy allows a client to make at all. Nothing here required a new grant, and nothing was found that needed one.
- **Judgment call — no UI control for `meetings.is_private`.** The product spec's "either party can mark a meeting fully private" is implemented with `meeting_participants.marked_private` instead, per this build's task brief: a *personal* veto only its owner can reverse, rather than a shared flag either party could silently undo on the other's behalf. `is_private` stays at its schema default (`false`) throughout this feature; a control for it, if wanted later, is a deliberate addition to make, not an oversight to fix.
- **The consent-state derivation — "waiting on you" vs. "waiting on them" vs. "shared" vs. blocked by a privacy override even when both consented — is a pure function with its own test file** (`apps/web/src/app/connections/[connectionId]/location-sharing.ts` / `.test.ts`), tested the same adversarial way the Connect Flow's state machines were (every consent combination swept against the privacy-override case, not just the happy path).

**Meeting feed landed 2026-08-13** (README build order item 4 — the last of the core Phase 1 pilot features; architecture §2.9; `apps/web/src/app/feed/`, `apps/web/src/server/feed/feed-service.ts`). A single `/feed` page listing every meeting the signed-in user is entitled to see, consuming `private.can_see_meeting()` and the `meetings`/`meeting_participants`/`meeting_locations`/`connections`/`users` policies in `20260809211200_rls_policies_graph_and_meetings.sql` and `20260809211100_rls_policies_identity_and_cards.sql` exactly as they already stood — no migration, no policy, and no line of `packages/core/src/connect/`, the Connect Flow API routes, or `apps/web/src/app/connections/**` changed, beyond the one new link a participant feed item makes into `/connections/[connectionId]`. Per §2.9, there is still no feed table: both post types are computed on every read from the same three tables the schema always had. Four things a reader should know:

- **The security boundary is one unfiltered `SELECT` on `meetings`, and every other query in the service layer just formats what RLS already decided.** `listFeedItems` (`feed-service.ts`) runs `select * from meetings order by occurred_at desc limit 50` through the caller's own RLS-bound client with no `.eq(...)`, no participant filter, and no mutual-of-both check written in TypeScript anywhere — `private.can_see_meeting()` is the only thing deciding which rows come back. This was verified by reading that function and the policy migration directly (not assumed from the architecture doc's prose) before any code was written, including confirming the `users` select policy's `are_connected` branch already permits reading *both* participants' profiles for a triadic post, since the viewer is by definition connected to both.
- **"You met X" vs "[A] met B" is a five-line pure function with its own adversarial test file** (`apps/web/src/app/feed/classify.ts` / `.test.ts`), following the same pattern as the connections feature's `location-sharing.ts`: given a meeting's participant ids and the viewer's id, it returns `"participant"` if the viewer is one of the two, `"mutual"` if not, and `null` — fail closed, skip the row — if the meeting isn't a well-formed two-participant row. It does not re-derive graph membership; that would duplicate the RLS check rather than trust it.
- **Location follows the same "never approximate" rule as everything else here.** `meeting_locations` is queried plainly, through the same RLS-bound client, for every meeting in view. For a participant's own meetings that's usually a row; for triadic posts it is almost always nothing, because sharing needs unanimous consent from participants who don't know this particular viewer exists at consent time — expected and correct, not a gap to work around.
- **Judgment call — a sane cap, not pagination.** The task's own sizing note (and §2.9's ~337-user scale) says pilot users have a single-digit number of meetings on day one; the feed is a plain reverse-chronological list capped at 50 rows, with no cursor, no infinite scroll, and no machinery aimed at a scale this product doesn't have yet. Worth revisiting — with real pagination, not a bigger number — once a pilot user's meeting count approaches the cap.

**Deployed to Vercel 2026-08-13** — the web app is live at `https://smart-card-2-0-web-smart-card1.vercel.app`, verified by fetching `/` and `/profile` directly rather than trusting a green build: `/profile` correctly renders the signed-out gate with a real `/api/auth/login` link, confirming the Kinde env vars resolve at request time in production, not just during the build's static analysis. Two things a reader should know:

- **Turborepo silently strips server-only env vars from a task unless `turbo.json` declares them, independent of whether Vercel has them set.** The build failed twice with `KINDE_ISSUER_URL is required` even after every variable was confirmed present on the Vercel project — the build log's own warning named the cause. Local dev never surfaced this because `next dev` reads `.env.local` directly, bypassing Turbo; only `vercel build`'s `turbo run build` path filters through `turbo.json`'s `env` list. Fixed by declaring the 14 server-only vars the web app reads on the `build` task (`turbo.json`) — `NEXT_PUBLIC_*` vars don't need listing, Turbo passes those through via framework inference.
- **Vercel Authentication (SSO protection) was on by default for the project's `*.vercel.app` URL** and was turned off deliberately so the app is reachable before `smartcard.tech` DNS is pointed here — custom domains bypass this protection automatically, so this only mattered because no custom domain is wired yet. Kinde sign-in remains the real gate for anything behind it; this setting only controlled who could load the page at all.
- **A pasted `SUPABASE_SERVICE_ROLE_KEY` came out of the browser corrupted, and it took a live production error to catch.** Every request past a successful Kinde login failed with `Cannot convert argument to a ByteString because the character at index 8 has a value of 8226` — a literal bullet character (`•`) sitting inside the key, most likely a Chrome password-manager overlay interfering with a bulk multi-line paste into Vercel's env var form. The build had nothing to say about it (a malformed secret is still a valid string at build time); it only surfaced once `ensureUser()` tried to use it as a real Supabase `Authorization` header at request time, verified by reading the actual runtime error via `get_runtime_errors` rather than guessing from the symptom. Re-entering that one value by itself, outside the bulk paste, fixed it. Worth remembering next time a long secret is pasted into a Vercel field: paste it alone, and if anything about the character count looks off, don't assume the paste was clean just because the form accepted it.

**Nav shell and home screen landed 2026-08-14.** Every screen — Profile, Feed, Connections, Connect — was previously reachable only by typing its URL, with no way to move between them, and `/` was still the placeholder that shipped with the initial scaffold. Three things a reader should know:

- **Fixed a real, pre-existing failure in the §4.7 static-analysis test while verifying this pass, unrelated to any of it.** `no-second-write-path.test.ts` was failing against the already-committed code before this session touched anything (confirmed by stashing and re-running against `HEAD`) — it couldn't distinguish a second *creator* of graph rows (the actual threat) from the narrow, RLS-scoped `.update()` calls the Connections feature legitimately added. **QR presenter froze on "Setting up your code…" in production, found by a real user testing the nav shell.** `presenter-flow.tsx`'s requesting-location effect dispatches `starting` partway through its own async body, before `createQrSession` resolves. Its dependency array is `[state.phase]`, so that self-dispatched phase change tore the effect's own instance down mid-flight, running the cleanup that set the `cancelled` flag the rest of that same instance was still checking — the session was created successfully (confirmed 201s in the runtime logs) and the `session-started` dispatch that renders the QR was silently dropped. The `failed` dispatch in the catch branch had the identical race, never reported because nobody had hit it yet. Per CLAUDE.md's model guidance for connection-security code, diagnosed here but fixed with Opus at high effort: replaced the cleanup-driven flag with a ref-based attempt id that only increments on a genuine new attempt (initial mount or `restart`), not on every phase change the effect causes on its own way to finishing. `scanner-flow.tsx` was checked for the same pattern and doesn't have it — its effects only ever dispatch as the last step of their sequence.

- **`SUPABASE_JWT_SECRET` must still not be revoked in the Supabase dashboard**, even though no code reads it any more. `SUPABASE_SERVICE_ROLE_KEY` is itself a legacy JWT signed with that secret, so revoking it would break `ensureUser()`. Retiring it for real means first swapping the service-role key for an `sb_secret_…` key — still tracked as Q31, still a separate piece of work. *(Update 2026-08-14: done — see the entry below closing Q31.)*

**Events landed 2026-08-14** (README build order item 5 — the last of the Phase 1 pilot features; architecture §2.6, and its new "Completed (2026-08-14)" subsection; `supabase/migrations/20260814051000`–`20260814051400`, `packages/core/src/events/`, `apps/web/src/server/events/`, `apps/web/src/app/(app)/events/actions.ts`). Cities, capacity, host approval, a waitlist, event cover images, and the two-count "who's going" hook. **Backend only — there are no screens**, by design: the project owner is building the UI separately, so this pass ships the schema, the policies, the RPCs, the service layer and the Server Actions those screens will call. Two long-open questions closed with it: **Q5** (anyone signed in may create an event) and **Q14** (no recurrence concept — one row per occurrence). Five things a reader should know:

- **Nobody can write an RSVP status any more, and that is the point of the whole pass.** The original policy let a client insert and update `event_rsvps.status` directly, which was fine when the four statuses were things you could truthfully say about yourself. Adding capacity and host approval changed what `going` *means*: a client that can write `going` can approve itself past the host's gate and take a seat at a sold-out event. Worse, `going` is one of the three branches deciding who may read whose profile (`shares_event_with`, §3.4) — so a writable `going` is a writable profile-visibility grant. All three write grants and all three write policies are now gone, and every transition goes through one of three `security definer` functions that compute the real status themselves while holding a lock on the event. This is the same shape `connections` and `meetings` have always had, for the same reason. Verified against the live database as a real authenticated user: direct `INSERT`, `UPDATE` and `DELETE` on `event_rsvps` are all refused with `42501`.
- **A "going" RSVP to an event that already ended is now refused, and that is a security fix rather than tidying.** Two people who both RSVP `going` to the same event can read each other's profiles. Without this check, every public event in the archive was a permanent standing invitation: pick a person, find an event they attended last month, tap "going", read their profile — no attendance, no contact, nothing they could notice or refuse. Now it takes a live, upcoming event both people are choosing to be at, which is the situation that rule was actually designed for.
- **The host's approval queue shows names, and that disclosure is contained in one function on purpose.** A host cannot approve a request from a name they can't see, so the queue has to reveal profile fields for people the host may not otherwise be able to read. The obvious way to do that — add a branch to the `users` read policy — was considered and **rejected**: that policy is what structurally forbids global search, and a branch there would apply to every query against `users` anywhere in the app, forever. Instead it is one `security definer` function that answers one question, for one role, about one event, and can't be composed into anything else. It deliberately excludes people who only tapped "interested", people who said no, and people already denied.
- **Waitlist promotion happens inside the transaction that frees the seat, never on a timer.** A seat filled "shortly after" is a seat that briefly belongs to nobody, and a queue where the next person can't take their own seat but anyone refreshing can is a race, not a queue. Withdrawing, changing your answer, or a host raising the capacity all promote from the front of the line (oldest first, tie-broken deterministically) in the same commit. Raising capacity from 1 to 3 with two people waiting promotes both, verified live; lowering it again demotes nobody, because an admission already given is not withdrawn by editing a number.
- **The city list is a placeholder and is meant to be edited.** Ten US metros are seeded so the feature works end to end; that is not a decision about where SmartCard operates. Cities are a curated table rather than free text (four spellings of "New York" within a week would break the only query browse needs) and rather than geocoded (that buys a vendor and an unresolved terms-of-service question — Q25 — to solve a problem the pilot doesn't have). Clients get SELECT and nothing else; editing the list is a service-role job. Deactivating a city hides it from browse without touching the history of what happened there — deleting one that has events is refused outright.

**`SUPABASE_SERVICE_ROLE_KEY` migrated off the legacy JWT format, closing Q31, 2026-08-14** (architecture §9, Q31; `apps/web/src/server/env.ts`). The service-role key `ensureUser()` depends on (§5.3) was still a JWT signed by the same shared secret Q27 moved per-request auth *tokens* off of — which meant that secret could never actually be revoked, no matter how completely Q27's ES256 migration was verified, because revoking it would have disabled `ensureUser()` along with it. Supabase's documented fix is a straight swap: create a new `sb_secret_…` key in Settings → API Keys and put it in the same variable. Three things a reader should know:

- **No code changed.** `supabaseServiceRoleKey()` (`env.ts`) already read the variable as an opaque required string with no format check, so the new key format is a drop-in replacement — the only work here was the dashboard swap plus deployment and verification.
- **Verified in the right order, not assumed from a clean build.** The new key was set in `.env.local` and on Vercel and production was redeployed; the swap wasn't called done until a real sign-in exercised `ensureUser()` against it — `/api/auth/kinde_callback` followed by `/`, `/profile`, `/feed`, `/connect`, `/connections` all returning 200 with zero runtime errors — because a corrupted-but-syntactically-valid secret is exactly the failure mode the 2026-08-13 deployment entry above already hit once, and it doesn't show up any other way.
- **Only then were the legacy keys retired, in the order Supabase's own docs require.** The legacy `anon`/`service_role` JWTs were disabled in Settings → API Keys first (confirmed via the Supabase API: the legacy `anon` key now reports `disabled: true`), and the deprecated JWT secret was revoked in Project Settings → JWT Keys only after that. The secret's revoked state has no API surface to check independently; everything checkable from here — the new key working, the legacy `anon` key disabled, zero runtime errors since — was confirmed directly rather than taken on the project owner's word.

**Reverse geocoding landed 2026-08-14, closing Q25** (architecture §2.4 amendment, §9; `apps/web/src/server/connect/geocode.ts`). `meeting_locations.place_label` had been null for every QR/GPS meeting since the Connect Flow pass, because the job that fills it needed a provider decision this pass makes. Two things a reader should know:

- **The provider choice turned on storage terms, not coverage or price** — checked directly rather than assumed, since this design retains the label instead of displaying and discarding it. Google's Geocoding API terms permit indefinite storage of `place_id` only, not the formatted address `place_label` actually needs; OSM Nominatim's policy is silent on storage and expects self-hosting past casual volume. Mapbox has an explicit `permanent=true` tier built for exactly this, so it's the one wired in. `GEOCODING_API_KEY` is optional, same posture as `EXPO_ACCESS_TOKEN`: unset means every meeting's `place_label` just stays null, never a blocked or failed connection.
- **One Mapbox call, not two.** Reverse geocoding with `types=poi,neighborhood,place` returns the nearest match for each type in a single response, so choosing between "a venue name" and "a generalized neighborhood+city label" (§2.4's judgment call) is a pure decision over features already in hand (`chooseLabel`, unit tested) rather than a second network round trip. `types` never includes `address`, so a bare street address is not a shape the response can even take. Runs after `create_verified_connection` commits, awaited so it can't be dropped by a frozen serverless function, but never able to fail the redeem response — same contract `push.ts` already established for the card-tap notification.

**Activity page landed 2026-08-14, closing Q28** (architecture §4.5's amendment, §9; `apps/web/src/app/(app)/activity/`, `apps/web/src/server/activity/activity-service.ts`, `apps/web/src/server/cards/cards-service.ts`). §4.7 threat 7's detection control had only ever had a push-notification half — real but best-effort, and §4.5's amendment is explicit that a user who misses or disables it needs another way to notice a stolen card. This is that other way: a new nav destination listing every tap of the caller's own card(s), each with an inline "remove connection," plus a "your cards" section with an inline "revoke." Two things a reader should know:

- **"Revoke card" had to be built from scratch, not wired up.** The RLS policy allowing an owner to revoke their own card has existed since the legacy migration, but nothing in the app — no Server Action, no service function, no button — ever called it, confirmed by grepping the whole repo before assuming otherwise. `apps/web/src/server/cards/cards-service.ts` is new; it exposes only revoke, not the restore half the same policy also permits, since nothing asked for that yet.
- **No new table, no new grant.** Both halves of this page read data that was already client-readable: `connection_sessions` (presenters can already SELECT their own rows) and `cards` (owners can already SELECT their own rows). The page's own query layer is the only new code on the read side.

**Private-event invites landed 2026-08-14** (architecture §2.6's "Private-event invites" amendment; `supabase/migrations/20260814060000`–`20260814060100`, `packages/types/src/db/event-invites.ts`, `apps/web/src/server/events/events-service.ts`, `apps/web/src/app/(app)/events/actions.ts`). Backend only, no screens, same as the Events pass. Two things a reader should know:

- **Three of the four things asked for in this pass already existed, and that's worth knowing before anyone re-requests them.** Only private-event invites were genuinely missing. Public events were *already* joinable by any signed-in user with no invite or link at all — that's the deliberate exception in the events read policy, and the absence of a gate is the feature. Waitlist auto-promotion was *already* unconditional, running inside the same transaction that frees the seat, with no per-event opt-in flag (one was deliberately not added). And the waitlist count was *already* visible to ordinary attendees as well as the host — only the `pending` count is host-only. The architecture amendment records each with its evidence.
- **An invite grants visibility, never an RSVP, and it can only reach someone you're already connected to.** The host or anyone actually `going` can invite; the person invited can then see the event and must still RSVP themselves. The connection requirement is the security-relevant half rather than politeness: two people who are both `going` to the same event can read each other's profiles, so without it you could create a private event, invite a stranger, and manufacture mutual profile visibility with no tap and no scan — the same hole the "no imported guest lists" rule closed, reached by a different route. The rejected shortcut was having the inviter write the invitee's RSVP row, which would have meant one person handing another person's profile visibility away on their behalf. Deliberately not built: un-inviting, because revoking an invite wouldn't remove the visibility of anyone who had already RSVP'd, so the obvious version would fail silently exactly where a host would expect it to work.

**Verified meetings now know which event they happened at, landed 2026-08-14** (architecture §2.6's "a verified meeting can now say which event it happened at" amendment; `packages/core/src/connect/event-tagging.ts`, `apps/web/src/server/events/events-service.ts`, `apps/web/src/server/feed/feed-service.ts`). `meetings.event_id` had existed since the original schema and never once had a value — both verifiers hardcoded it to null. Two things a reader should know:

- **QR only, automatic, and it cannot affect whether a connection is accepted.** A meeting gets tagged when both people RSVP'd `going` to the same event and both GPS fixes the proximity gate already compared land within its venue radius; two simultaneously-matching events leave it untagged rather than guessing. It runs strictly after the existing nine-step GPS/graph/rate-limit gate has already accepted the scan — proven with a 12-scenario × 3-world test showing every refusal reason is identical whether a matching event exists or the events lookup throws, and that the lookup is never even called on a refusal. NFC stays untouched (no GPS gate, nothing to match against a venue) — a deliberate scope cut, not an oversight.
- **This is what makes "how many connections were made here" and "which event did the feed say this was" answerable at all**, now that a real tag can exist: a `connections_made` count on the event page (visible to anyone who can see the event, same as going/interested), a personal "how many did I connect with" number that needed no new grant, and an optional event name on feed posts. The personal count caught a real bug before it shipped — the obvious version over-counted by including meetings only visible through the feed's triadic "mutual of both" rule, not meetings the caller was actually part of.

**The design system and navigation shell landed 2026-08-14 — phase 1 of implementing `docs/design/DESIGN.md`** (`apps/web/src/app/globals.css`, `layout.tsx`, `(app)/nav.tsx`, `(app)/layout.tsx`). The design spec and its Design Lab prototypes were committed earlier the same day as *documentation only* — that commit said so explicitly ("nothing here touches `apps/web`") — so the live app still looked nothing like them. This is the first pass that actually applies any of it. Four things a reader should know:

- **Events is now reachable.** The dock has seven slots and Events is one of them; until now its complete backend had no route at all, so the feature existed for nobody. `/events` currently renders a scaffold that says the screen is being built rather than an "empty state", because there may well be events and the page simply cannot show them yet — claiming otherwise would break §7's rule against implying a capability that isn't there. The real browse screen is phase 2.
- **Home is deliberately the centre slot, and "Connections" is now labelled "People".** Both come from the prototype's nav list, which states the reason: the destination you always return to should be the easiest thumb target, with discovery to its left and your own network and identity to its right. The order in `NAV_ITEMS` is therefore load-bearing, and the file says so.
- **Dark mode is gone, on purpose.** The scaffold's `prefers-color-scheme: dark` block was deleted rather than extended. `DESIGN.md` opens with "never dark" and defines exactly one palette, and its glass surfaces are translucent *white* over a light canvas — on a dark ground the whole system is illegible rather than merely different. Restoring it is a design deliverable first, not a CSS one. A `prefers-reduced-motion` block was added in the same pass, since the prototypes animate freely and a shipped app must not.
- **The two handed-over artifacts disagreed on the accent colour, and the rendered one won.** `DESIGN.md`'s table documents `#0a84ff`; every prototype actually renders `#0b60ff`, and its `--accent-deep`/`--accent-tint` are computed from it. The brief was to build the screens exactly as designed, so `#0b60ff` ships and the discrepancy is recorded in `globals.css` next to the token rather than quietly resolved.

See the architecture proposal for the full stack, schema, RLS strategy, and connection-verification design; §3.6 records the judgment calls made while implementing the schema, and the 2026-08-13 amendments record theirs the same way. Build order for the first pilot:

1. Profile
2. Connect flow — NFC + QR/GPS (highest security priority)
3. Mutual connections + meeting record
4. Meeting feed, including the triadic "A met B" post
5. Events — RSVP + "who's going"

Messaging and the non-user landing/pending-connection flow are deferred past the first pilot.

## Getting started

**Prerequisites:** Node 22+, and [Corepack](https://nodejs.org/api/corepack.html) enabled (`corepack enable && corepack prepare pnpm@latest --activate`) — this repo uses pnpm workspaces + Turborepo, pinned via `packageManager` in `package.json`, so plain `npm`/`yarn` won't work correctly here.

```sh
pnpm install
```

**Web (Next.js):**

```sh
pnpm --filter web dev
```

**Mobile (Expo):**

```sh
pnpm --filter mobile start
```

NFC work later in the build order needs an EAS development build, not Expo Go — see `docs/architecture/` §7.2.

**Environment variables** come from a single `.env.local` at the repo root (gitignored — never committed). Both apps' dev scripts load it directly rather than keeping a per-app copy. If it's missing, ask the project owner for values.
